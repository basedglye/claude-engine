### 1b. Why the lane concluded otherwise — its driver, not the screen

`apps/hotel/dev/playtest.mjs:390-396`:

```js
const docFields = Object.values(snap2.comps.document).find((d) => d.ownerEntity === guestEntity)?.fields;
...
for (const key of Object.keys(docFields)) {
  if (key in res.fields && String(docFields[key]) !== String(res.fields[key])) { ... }
}
```

Two independent bugs:

1. `.find(...)` takes only the **first** document the guest owns. A guest
   carries two (`id` and `resSlip`), so half the fields were never in the
   comparison at all.
2. `key in res.fields` compares **same-named** keys. The ID's field is
   `name`; the reservation's is `guestName`. A `name-mismatch` — the
   headline fraud — can therefore *never* appear in that diff. Nor can
   `id-expired`, `id-missing`, `res-slip-missing` or `blacklisted`, none
   of which are same-name value comparisons.

B3's actual sentence — "the raw field-name diff … did not surface an
obviously different KEY" — is an artifact of that code. It is not a
statement about the RESERVA screen. **B3 as written: REFUTED.**

### 1c. The real blocker the lane's method concealed

**F1 (P0, new) — the shipped game has fraud switched off.**

`apps/hotel/src/sim/game.ts:329`:

```ts
export const DEFAULTS: ScenarioConfig = { ... fraudRatePermille: 0, ... };
```

`game.ts:364` `setup(sim)` → `setupWithConfig(sim, DEFAULTS)`, and
`apps/hotel/src/main.ts:78` calls `setup(sim)`. `main.ts` reads exactly two
URL parameters (`worldforgeSeed`, `worldforgeStartPaused`, lines 76 and
264) — **neither overrides the config.** Only harness scenarios override
the rate (`fraud-catch`/`first-hire` 500, `escalation-stars` 1000).

Consequence: in the dev app **and** in the single-file artifact,
`guestFraudRng.int(0, 999) < 0` is never true, so `plantedViolations` is
always `[]` and **no guest is ever fraudulent**. Confirmed empirically: I
served and denied/accepted through seven consecutive presenting guests on
`hotel-alpha-loop-1` (`artifacts/coo-b3/probe3.log`,
`legit-reserva-{2,4,6,9,11,13}.png`), every one `planted=[]`.

VISION's loop step and BREAKDOWN-2 §4 row 3 ("**A fraud is caught**, by the
player noticing it") are therefore **unreachable in the product**, and the
best-designed screen in the game has nothing to do. This is the single
most important finding of cycle 2 and the lane did not have it.

It also means the lane's B3 sentence *"During my session's only fraud
case…"* describes an event that could not have happened on the build it
was playing. That claim must be withdrawn.

**Fix-list item F1 (sim lane, cycle 2, P0)** — not C2-W1's, it may not fix
anything:
> Give the shipped game a non-zero fraud rate. Preferred shape: keep
> `DEFAULTS.fraudRatePermille = 0` (13 headless gates golden-verify streams
> built on it — changing it moves every hash), and instead have
> `main.ts` call `setupWithConfig(sim, { ...DEFAULTS, fraudRatePermille: N })`
> with `N` chosen by the CEO/design (the escalation scenarios use 500;
> something in 150–300 is the obvious starting proposal for a first-time
> player). `setupWithConfig` is already exported. Because the app's config
> is not what any harness scenario constructs, no gate hash moves — but the
> browser gates run against `main.ts`, so re-run all five and re-pin
> `fps-look-interact`'s command count if it shifts. Add a headless gate
> that asserts the *app's* config produces at least one
> `plantedViolations.length > 0` inside 14 days, so this can never silently
> regress to zero again.

## 3. B7 (H key) — **NOT A CONFIRMED DEFECT**; the lane's check window was wrong

`apps/hotel/src/main.ts:580`:

```ts
if (e.code === "KeyH" && !e.repeat && !focusedScreen) walkthrough.skip();
```

H is **deliberately gated on no terminal screen being focused** (a focused

The lane pressed H "at tick 24,377, deep into the session, after the
RENOVATE press attempts" — i.e. almost certainly with LEDGER focused, in
which case the handler is *supposed* to do nothing. B7 is a bad check
window, and the lane was right to flag it against itself rather than
assert a bug.

No fix-list item. **Re-run item R1**: check H in isolation, on a fresh
run, before any terminal is focused, asserting `data-visible` goes 1 → 0

## 4. B2 (no time acceleration) — **RESOLVED, PENDING VERIFICATION**

Per the CEO's ruling the orchestrator has landed host-side time
compression, and I confirmed it is in the tree
(`apps/hotel/src/main.ts:325-337`):

```ts
if (fastForwardHeld && !focusedScreen) {
  for (let i = 1; i < FAST_FORWARD_STEPS; i++) { sim.step(); hook.notifyTick(sim.tick); }
}
```

Hold **T**, 8 sim steps per host tick, disabled while a screen is focused
and never held by the harness. Replay-identical by construction — commands
are tick-stamped and the sim is a pure function of (seed, command log), so
running more steps per frame changes no hash. The comment says exactly
this. I used it in my own probe (`ff()` in `probe3.mjs`) and the page
stayed alive and deterministic across it.

**Not yet verified, and the playtest lane owes all of it on the re-run:**

1. **B2's own claim, re-measured with T held.** 84,000 ticks at 8× is
   ~9 real minutes of held-T waiting instead of ~70. Report the real
   wall-clock, door-to-end-card, and say whether it now reads as "one
   sitting".
2. **T is discoverable.** The entry overlay's control list (which B6
   verified as accurate and complete) does **not** mention T. As of this
   change it is now incomplete — either the overlay gains "T fast-forward"
   or T is undiscoverable and the fix does not land for a real player.
   Re-check `.hud-controls` text and file it as a blocker if T is absent.
3. **The focus gate behaves.** Hold T with a terminal focused and confirm
   the sim does *not* accelerate.
4. **Replay identity, empirically.** Play a session with T held at
   arbitrary moments, save/restore (F5/F9) or re-run the same command log,

5. **The artifact too**, not only the dev app: hold T in
