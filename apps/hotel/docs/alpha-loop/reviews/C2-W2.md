## 1. Carry 1 — the sun-shadow streaks. **Landed, and better than required.**

BREAKDOWN-2 §2.2 offered two acceptable fixes and asked the lane to pick
one with justification. It implemented **both**, which is the right call
because either alone is leaky here:

- **Ortho clamp** (`lighting.ts:205-233`): `halfW` from the street's own
  width, and — the part that actually matters — `cam.far` derived from the
  street's *depth* rather than reusing `halfW`. The comment at 221-232
  explains exactly why (the street strip is shallow; a `far` sized off the
  width overshoots several times past the facade). That is the reasoning of
  someone who looked at the geometry, not someone tuning a number.
- **Layer restriction** (`lighting.ts:36-42`, `:245`, `:283`):
  `SUN_SHADOW_LAYER = 1`, enabled on the exterior group only
  (`exterior.traverse(...layers.enable(...))`) with `cam.layers.set(...)`
  on the shadow camera. This is what stops interior architecture
  *self-shadowing as a caster* even when it sits inside the clamped box —
  a case the ortho clamp alone cannot reach, and the comment says so.

Shadows are not disabled anywhere; `sun.castShadow = HIGH_QUALITY` stands,
so `fps-look-interact` and the tier-2 look keep what they depend on.

**Residual, confirmed by eye:** comparing
`TRUEBEFORE-tier0-spawn-yaw0.png` against `after-tier0-spawn-yaw0.png`, the
hard diagonal bands across the left-hand exterior wall are largely gone but
a **faint diagonal streak survives** in the same place. That is the fence
bleed the lane admits. The orchestrator's routing —
`castShadow = false` on the fence and rope, cycle 3 — is the correct fix and
for the right reason: the fence is inside the exterior group and therefore
on `SUN_SHADOW_LAYER`, so the layer restriction deliberately keeps it a
caster. **Agreed, deferred, recorded.**

**Carry to the COO sweep (C1):** `after-tier0-spawn-yaw0.png` reports
`frame: 11.1ms` where `TRUEBEFORE-...` reports `3.2ms`. These are single
frames at different ticks and are *not* a measurement — but a shadow-camera
change is exactly the edit that can cost frame time, and eyeballing a HUD
counter is not how this project decides. Take the number from
`fps-look-interact`'s verdict JSON on the merged tree and compare it to
cycle 1's, rather than from the screenshots.

## 2. Carry 3 — `overflowWaitCells` dedupe. **Landed. It is a GUARD, not a fix.**

The code is right. `game.ts:734` builds `candidateWaitCellIdx` from
`candidateWaitCells`, and the overflow scan skips any cell in it
(`if (candidateWaitCellIdx.has(idx)) continue;`). Deterministic throughout:
built from sorted arrays, no `Rng`, no float, no bare object-key iteration,
`found.sort((a,b) => distSq || idx)` for a stable tie-break.

**But the hash tells us something the lane's report should say out loud.**
BREAKDOWN-2 §3 and §5 rule 4 *predicted the hashes would move* — excluding
a cell from a pool changes which cell a guest is assigned, which changes the
command stream. The lane reports, and `artifacts/verdicts/alpha-loop.json`
confirms, `finalStateHash: 402826283` — **cycle 1's value, unchanged**.

That is not a contradiction; it is a result. If the filter had removed any
cell that was actually being assigned by rank, the ranks below it would
shift and the hash would move. It did not. Therefore, on every seed the 13
gates cover, **`candidateWaitCells` and `overflowWaitCells` never actually
overlapped.** reviews/W1.md §6 carry 1 described a *latent* defect — real in
the code, never live in any gated run.

So the deliverable here is the **regression guard**, and it should be
described that way in the handoff. Two consequences worth recording:

- The new assertion (`alpha-loop.scenario.mjs:201-202`, zero
  `nav.sharedWaitCellPool` events) is **tautological by construction**: the
  `continue` at `game.ts:753` makes `sharedCount` necessarily zero. It can
  only red if someone deletes that line — which is precisely the regression
  it is there to catch, and the lane's perturbation exercised exactly that.
  Legitimate, but it is a *structural* guard, not a behavioural one, and a
  future reader should not mistake it for evidence that guests ever shared a
  wait cell.
- **Carry to cycle 3 (C2):** if the intent is to prove the two pools can
  never overlap *for any floor*, the honest form is a setup-time invariant
  (assert the intersection is empty at construction, for whatever floors are
  generated) rather than a per-run event count on one seed. Cheap, and it
  generalises past `hotel-alpha-loop-1`.

## 3. Carry 4 — the broke-`renovateCommand` bot beat. **Landed, and carefully.**

`renovateProbeBot` (`alpha-loop.scenario.mjs:83-104`) is the best-argued
piece of this lane. It fires **once**, and only when:

1. `hotel.tier === 0`,
2. `hotel.stars >= RENOVATE_STAR_REQ[1]` — so the stars gate is already
   satisfied and **cash is the first failing check**, and
3. `hotel.cash < RENOVATE_COST_MINOR[1]` — still broke, and
4. the player is inside `DESK_RADIUS_MM` — so the range check passes.

The comment records that the first pass reddened on `stars-too-low` instead
and that the ordering was corrected. That is `applyRenovate`'s real
validation order (range → max-tier → stars → cash) being respected rather
than guessed, and it makes the assertion mean the one thing it is supposed
to mean.

And it guards its own non-vacuity: assertion 1
(`alpha-loop.scenario.mjs:112-114`) asserts `renovateProbeTick !== null`,
with the description "otherwise every assertion below it is vacuous". This
is the brief's own non-vacuity principle applied *inside* the scenario,
unprompted. Noted and credited.

**Signature check:** the probe adds a `hotel.renovate` command to
alpha-loop's replay log while leaving `finalStateHash` at 402826283. That is
exactly the fingerprint of a correctly-refused command — the log grows, the
state does not — and `--verify-replay` reconstructs from the same log, so
the golden stays self-consistent. Correct.
