## Verdict: **FIX-LIST** (four blockers, three rough-edges)

The solver itself is the right idea and mostly well built: a 0.25 m
occupancy grid, wall-run merging, door lanes baked in before any query,
deterministic tie-breaks, no `Math.random()`, and every placement function
returning `undefined` rather than guessing. It is presentation-only and
lives under `src/render/`, so its `Math.PI`/`Math.hypot` use breaks no
purity root (`scripts/check-purity.mjs` enforces `apps/hotel/src/sim`, not
`src/render`) — no invariant issue.

The failures are all in the **seam** between the solver and its callers:
one function that promises less than callers assume, and two call sites
that ignore the contract the solver spells out in its own doc comment.
Both of the specific things you asked me to confirm are real, and I can
name the line that causes each.

## 1. Blockers

### P1 — `placeOnWallSurface` marks no occupancy, so every painting in a loop lands on the same spot

`placement.ts:288-306`, doc comment included: *"Does not mark occupancy
(wall-mounted, no floor footprint)."* It is a pure query — it finds the
longest free run on the best side, returns its centre, and changes nothing.

`decor.ts:619-627` (lobby) and `decor.ts:688-696` (corridor) then call it in
a loop:

```js
for (let i = 0; i < 4; i++) {
  const pose = placeOnWallSurface(occ, 0.7, 0.5, ["west", "east"]);
  if (!pose) break;
  ...painting.position.set(pose.x, 1.5, pose.z);
}
```

Nothing changes between iterations, so **every iteration returns the
identical pose** and all 2 / 4 paintings are stacked co-planar at one point.
Visible in the frames: `corridor-t2.png` requests four paintings and shows
exactly one gold frame; `lobby-west-t2.png` shows two gold panels
overlapping each other low on the same wall.

**Fix:** give wall-mounted items their own occupancy channel — e.g. a
second `Uint8Array` per wall side inside `RoomOccupancy` (`blockWallSpan` /
`isWallSpanFree`), marked by `placeOnWallSurface` with the item's width plus
a margin. Floor occupancy must stay separate: a painting above a dresser is
legal, two paintings on the same span are not. The loops in `decor.ts` then
work unchanged, and `break` on `undefined` starts meaning what it reads as.

### P2 — Both cart call sites break the solver's stated contract and drop the cart in the walkway

`placement.ts:226-229`: *"Callers **MUST** handle `undefined` by omitting
the item."*

`decor.ts:631-638` and `decor.ts:699-706` do the opposite:

```js
if (cartPose) { cart.position.set(cartPose.x, 0, cartPose.z); ... }
else { cart.position.set(room.xM0 + 0.4, 0, room.zM0 + 0.6); }   // unvalidated
group.add(cart);                                                  // added either way
```

The fallback is a hard-coded offset from the room's min corner with **no
occupancy check, no door-lane check and no wall alignment** — exactly the
class of placement this lane exists to delete. **Confirmed** as the cause of
what you saw: in `corridor-t2.png` the housekeeping cart sits at an angle
half-buried in the left wall's wainscot with its other end out over the
carpet, in the walking lane. The light nightstand standing free in the
middle of the same corridor is the same failure in another item.

**Fix:** delete both `else` branches and move `group.add(cart)` inside the
`if`. An omitted cart is correct behaviour; a cart in the corridor is not.
Then audit every other call site in `decor.ts` for the same shape.

### P3 — Wall lights are placed outside the solver and land on top of the paintings

**Confirmed.** `room4-doorway-t2-yaw90.png` shows the sconce drawn directly
over the top-left corner of the gold picture frame; `corridor-t2.png` shows
the same overlap, plus a second fixture half-buried in the wall/wainscot
junction at the left. `decor.ts` has no `sconce` symbol at all — the wall
lights come from another module and therefore share no occupancy with the
paintings, so the two systems independently pick "the middle of the nicest
wall".

**Fix:** route wall lights through the same wall-surface channel P1 adds,
placed **after** paintings so the paintings' spans are already blocked; or,
if the lights must stay where the architecture puts them, have
`buildOccupancy` block their spans before any painting query runs. Either
way the two must share one grid.

### P4 — A pilaster stands through the front desk

`lobby-west-t2.png` and `desk-t2.png`: a white pilaster is planted in the
middle of the desk run, cutting the counter and the clerk in half. The desk
rect is already known to the solver (`buildOccupancy`'s `deskRect` blocks
the footprint plus queue and clerk cells, `placement.ts:143-149`) — but
pilasters are architecture, generated before decor and not consulted
against it, so the block does nothing for them.

**Fix (owner: whoever owns pilaster generation, not necessarily this lane):**
exclude the desk rect + `CELL_M` margin from pilaster candidate positions.
This is the same root cause as P3 — architecture and decor solve
independently — and if one change fixes both it should.

## 3. What PASSES, checked rather than assumed

- **The sim-prop snap keeps interaction sane. Confirmed.**
  `upkeep.ts:369-380` computes `posM` from the sim's `pos` component and only
  ever writes `object.position` / `object.rotation.y` — the sim value is
  untouched, and `registerInteractable` still registers against the sim pos.
  `snapToNearestWall` (`placement.ts:345-363`) rejects any wall farther than
  `maxSnapM = 0.9`, and each snap moves the prop along **one** axis only
  (west/east change `x` and keep `z`; north/south the reverse). So the
  visual is at most **0.9 m** from the interaction point, comfortably inside
  `INTERACTABLE_RADIUS_MM = 1500` (`game.ts:161`) — the 1.5 m bar you set is
  met by construction, with 0.6 m of headroom. A prop whose `pos` is outside
  its room's rect (`d.d < 0`) is correctly left unsnapped rather than
  teleported.
- **Beds are headboard-to-wall.** `placeAgainstWall` returns `wallPoint`'s
  yaw, which is documented and implemented as back-to-wall / front-into-room
  (`placement.ts:211-224`), and `decor.ts:744` places the bed with the same
  pose. No frame contradicts it; the bedroom frames that would show it
  head-on are the four broken poses in R2, so this is "consistent with the
  code and with what is visible", not "proved by a frame". Re-shoot per R2
  and it closes.
- **Door lanes.** `buildOccupancy` blocks every door rect plus a 1 m lane on
  the swing axis *before* any query (`placement.ts:130-142`), and the lobby
  gets the entrance↔corridor straight lane on top. Nothing solver-placed can
  land in a door lane. The items that *do* sit in traffic (P2) got there by
  bypassing the solver, which is the point.
- **Determinism.** No `Math.random()`; the only tie-break is `run.len`,
  and seeds are `room.roomId * 31` / `* 97`. Iteration is over arrays, not
  object keys. Presentation-only, never hashed into sim state.
- **The debug switch is gone.** `placement.ts:131-133` now carries only the
  comment recording that it existed and how to re-run the check. Correct per
  CLAUDE.md ("no dev/debug commands reachable from production builds").
